# Intent Statement — AIネイティブ Webアプリ雛形

> Status: Draft (awaiting approval gate)
> Stage: intent-capture (Ideation)
> Lead: aidlc-product-agent / Support: aidlc-architect-agent

## Problem Statement（解決する課題）

生成AI・AIエージェントを使えばWebアプリのコードを高速に書けるようになったが、現状は **「速いが品質がばらつく」** という壁がある。個人エンジニアが「作りたいアイデア」を素早く動く形（プロトタイプ）にしようとすると、環境構築・定型実装・テスト・セキュリティ・デプロイといった周辺作業に時間を取られ、結局スピードが出ない。また、人やセッションによって成果物の構造・品質が変わり、再現性がない。

そこで本イニシアチブでは、**ソースコードを完全にAI生成させる前提で、一定以上の品質を自動的に担保する「雛形（スターターテンプレート＋ガードレール）」** を提供する。アイデアを素早く形にしつつ、生成物がそのまま本番運用に耐える品質・デプロイ可能性を持つ状態を、人手のレビューに依存せず仕組みで保証することを狙う。

**核心テーゼ:** 速度（バイブ開発）と品質（本番運用に耐える）の両立。どちらか一方ではなく、両方を「型」と「自動ゲート」で同時に成立させる。

## Target Customer（対象顧客）

- **一次利用者（Primary）:** ソフトウェアエンジニア（個人開発・少人数）。生成AIを開発の主役に据えて、アイデアを素早く本番品質のWebアプリにしたい層。
- **痛み（Pain）:** AI生成コードの手直し・レビューコスト、立ち上げの定型作業、品質・セキュリティの担保が属人的、プロト止まりで本番化できない。
- **将来の拡大対象（Secondary, 横展開）:** 同じ「型」をチーム・組織で共有し、再現性のある開発を回したい開発チーム／プラットフォームチーム。一次は個人だが、将来的にチーム・組織へ展開していく前提。

## Success Metrics（成功指標 — 測定可能な成果）

| 指標 | 測定方法 | 目標の方向性 |
|------|----------|--------------|
| **採用・再利用数（主要KPI）** | 雛形を採用したプロジェクト数・チーム数 | 増加（横展開の広がり） |
| 開発リードタイム | アイデア着手→動くアプリ（デプロイ）までの時間 | 短縮 |
| 品質ゲート通過率 | テスト・Lint・型・セキュリティが自動で「緑」になる割合 | 高水準を維持 |
| AI生成コードの手直し率 | 生成後に人手で修正した行・レビュー指摘数の割合 | 低減 |
| 本番到達率 | 雛形から生成したアプリが本番運用に至った割合 | 向上（プロト止まりを減らす） |

> 注: 主要KPIは「採用・再利用数」。ただし採用が広がる前提条件として、リードタイム短縮と品質ゲート通過率が満たされている必要があるため、これらを先行指標として併走測定する。具体的な数値目標は scope-definition / requirements-analysis で定量化する。

## Initiative Trigger（なぜ今か）

**市場・競合のスピード向上。** 生成AI/エージェント技術が実用水準に達し、より速い開発サイクルが競争上必要になった。「速く作る」だけなら既存ツールでも可能になりつつあるが、**「速く、かつ本番品質で作る」** を仕組みで提供できる型はまだ一般化していない。ここに先行して取り組む価値がある。

## Initial Scope Signal（初期スコープの示唆）

- **スコープ:** `feature`（新規開発、Standard深度、全フェーズ通し）。
- **成果物の到達点:** 本番運用まで。プロトタイプを速く出しつつ、そのままAWSで本番運用に耐える品質・デプロイを提供する。
- **対象アプリ形態:** フロントエンド + バックエンドAPI + DB のフルスタックWebアプリ。
- **技術スタックの示唆:** モダンTypeScriptフルスタック（例: Next.js/React + Node系 + DB）。本番デプロイ先はAWS（サーバレス／AWSネイティブを志向）。
- **品質担保の柱（4本）:** ①自動テスト（ユニット/統合/E2E）②静的解析・Lint・型チェック・フォーマット強制 ③セキュリティ（脆弱性スキャン・シークレット検出・入力検証）④動くデプロイ可能性（CIが通り実際に動く）。可読性・保守性・一貫アーキテクチャも付随価値として歓迎。

> これらは ideation 段階の初期シグナルであり、feasibility / scope-definition で技術的実現性・優先度・境界を確定する。実装詳細（具体的フレームワーク選定やAWSサービス構成）はこの段階では確定しない。

## Open Questions（次ステージで詰める論点）

- 「雛形」の提供形態は何か（CLIジェネレータ／リポジトリテンプレート／AI-DLC的なワークフロー／その組合せ）。
- 品質ゲートの具体的な合格基準（カバレッジ閾値、許容する脆弱性レベル等）の定量化。
- 「完全にAI生成」と「人のレビュー最小化」をどこまで厳密に適用するか（人の介入ポイントの設計）。
- AWSのどのデプロイモデルを既定とするか（サーバレス中心 / コンテナ / 両対応）。
