# Stakeholder Map — AIネイティブ Webアプリ雛形

> Status: Draft (awaiting approval gate)
> Stage: intent-capture (Ideation)

## Key Stakeholders（主要ステークホルダーと関心事）

| ステークホルダー | 役割 | 主な関心事（Interest） |
|------------------|------|------------------------|
| **個人エンジニア（一次利用者）** | 雛形を使ってアプリを作る | 速く動く形にできること、手直しが少ないこと、そのまま本番に出せること |
| **プロジェクトオーナー（本イニシアチブ）** | 雛形そのものの企画・推進 | 採用・再利用が広がること、速度と品質の両立というテーゼの実証 |
| **将来の開発チーム（横展開先）** | チームで同じ型を共有 | 再現性、オンボーディングの容易さ、チーム標準への適合 |
| **プラットフォーム／基盤チーム** | 雛形を配布・運用する立場（将来） | 保守性、ガードレールの一貫性、セキュリティ・コンプライアンス |
| **生成AI／AIエージェント** | コード生成の実行主体 | 明確な型・制約・合格基準（AIが従いやすいガードレール設計） |
| **エンドユーザー（生成アプリの利用者）** | 生成されたWebアプリを使う | アプリが動くこと、安全であること（間接的関心） |

## Decision-Makers vs Influencers（意思決定者 vs 影響者）

**意思決定者（Decision-Makers）**
- **プロジェクトオーナー（本イニシアチブの依頼者）** — 雛形の方向性・スコープ・品質基準を最終決定。各承認ゲートの承認者。

**影響者（Influencers）**
- **個人エンジニア（一次利用者）** — 採用可否を通じて成功を左右する実質的な評価者。
- **AIエージェント設計の制約** — ガードレールがAIにとって従いやすいかが、生成品質に強く影響。
- **AWS等のプラットフォーム制約** — デプロイ・運用の前提条件を規定。

## Communication Requirements（コミュニケーション要件）

- **承認ゲート:** 各ステージ完了時に本人（プロジェクトオーナー）が Approve / Request Changes を判断。AI-DLCワークフローの標準ゲートに従う。
- **意思決定の記録:** 主要な設計判断（スタック選定、品質ゲート基準、提供形態）は ADR / アーティファクトとして `aidlc-docs/` に残し、再現性とトレーサビリティを担保。
- **横展開時:** 将来チーム/組織へ展開する段階で、利用ガイド・オンボーディング資料が別途必要（construction/operation 以降で検討）。

## Notes

- 現時点の利用者は個人中心だが、成功指標は「横展開（採用・再利用数）」を据える。したがってステークホルダー設計も「個人が使いやすい」と「チームで再現できる」の両立を意識する。
- 本マップは ideation 初期版。scope-definition / team-formation で関係者と意思決定構造を精緻化する。
